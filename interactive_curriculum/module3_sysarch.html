System Architecture & Multi-Process IPC

How the physics loop, C++ memory injection hooks, loopback sockets, shared memory, and PyTorch tensors coordinate at 80× physical acceleration to train at ~197 aggregate FPS.

01. INTUITION

The Wind Tunnel vs The Telemetry Engineers

🏎️

Why Training a Neural Network Inside the Game Loop Kills Performance

Imagine if every time a racing car turned a corner on the track, the driver had to turn off the engine, step out, walk into a data center, wait 4 minutes for engineers to train a neural network on an NVIDIA GPU, get back in, and turn the wheel 2 degrees.

That is what synchronous single-process RL looks like. In Python, the Global Interpreter Lock (GIL) ensures that only one CPU thread executes Python bytecode at any moment. If the game physics and gradient backpropagation share the same thread, both grind to a halt.

The Solution: Asynchronous Decoupling. Two separate game instances run in their own native processes at 80× physical acceleration, dumping sensor logs into a shared memory buffer. Simultaneously, a dedicated Learner process drinks from that buffer and backpropagates gradients uninterrupted.

Stage 1: TMInterface C++ Memory Injection Hook
TmForever.exe <---> TMInterface.dll
TrackMania Nations Forever (2008) is a 32-bit DirectX 9 game. TMInterface (created by Donadigo) injects into TmForever.exe's process memory space. It intercepts the internal physics simulation loop (OnSimulationStep). Instead of letting physics run in real-time wall-clock time, it freezes the game loop and exposes a TCP loopback socket server on 127.0.0.1:8478 / 8479.
03. SIMULATION MATH

The 80× Sim Speed Setting vs Measured FPS Mystery

An interviewer will ask: "You set running_speed = 80 in TMInterface. Does that mean your simulation runs at 8,000 FPS?"

⏱️

The Speed Limit vs The Engine Throttle

In TrackMania, the real-time physical physics engine ticks at 100 Hz (\(1\text{ tick} = 10\text{ms}\)).
When you send C_SET_SPEED(80), you are telling the C++ engine: "Do not sleep between physics ticks. Advance simulation time up to 80× real-time if the CPU can compute it."
Target maximum tick rate: \(100\text{ ticks/s} \times 80 = \mathbf{8,000\text{ physics ticks/s}}\).

Why did we measure ~197 aggregate FPS in reality?
Because each RL action is held for 5 physics ticks (50ms). That caps the theoretical action step frequency to: \[\frac{8,000\text{ ticks/s}}{5\text{ ticks/action}} = \mathbf{1,600\text{ action steps/sec}}\] Furthermore, DirectX 9 rendering surface presentation, Windows GDI frame capture, TCP serialization, and local PyTorch neural net inference take real CPU time (\(\approx 8-10\text{ms}\) per step). Two collectors running simultaneously on 4 vCPUs saturate the CPU cores, delivering an aggregate empirical throughput of ~197 FPS!
